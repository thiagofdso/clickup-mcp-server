# Repository Guidelines

## Project Structure & Module Organization
- `src/` holds all TypeScript sources: `index.ts` is the CLI entry point, `server.ts` wires transports, and `sse_server.ts` serves HTTP/SSE traffic.
- `src/services/clickup/` wraps ClickUp API calls; keep shared helpers in `src/services/shared.ts`.
- Place cross-cutting logic in `src/middleware/`, reusable utilities in `src/utils/`, and MCP tool definitions under `src/tools/`.
- Compiled JavaScript lands in `build/` (generated by the TypeScript compiler); avoid editing files there directly.
- `scripts/` contains operational helpers such as `generate-ssl-cert.sh` and `run-test.ts`; `docs/` and `assets/` store reference material and supporting artifacts.

## Build, Test, and Development Commands
- `npm install` – install dependencies (Node 18–22 supported).
- `npm run build` – compile TypeScript to `build/` and set the CLI executable bit.
- `npm run start` – run the compiled server from `build/index.js`; ensure environment variables are loaded.
- `npm run dev` – watch-mode compilation for rapid local feedback.
- `npx ts-node scripts/run-test.ts src/tests/example.test.ts` – compile and execute a targeted test file (adjust the path to your test).

## Coding Style & Naming Conventions
- Use TypeScript modules (`type: "module"`, NodeNext resolution) and prefer named exports from feature modules.
- Follow the established two-space indentation, `camelCase` for functions/variables, and `PascalCase` for classes/types.
- Organize files by capability (transport, services, tools) and mirror runtime folder names when adding new directories.
- Run Prettier (if configured in your editor) or rely on `tsc` for basic structural checks before committing.

## Testing Guidelines
- Co-locate new tests inside `src/tests/` or beside the feature as `*.test.ts`; compile and run them through `scripts/run-test.ts`.
- Capture integration scenarios in `mcp_test_plan.md` and update it when workflows change.
- Ensure new MCP tools include request/response examples and verify them against the ClickUp sandbox before submitting.

## Commit & Pull Request Guidelines
- Match the existing Git history: concise, present-tense summaries (e.g., “Atualiza serviço SSE”); include a context prefix only if it clarifies scope.
- Reference linked issues and note config/env impacts in the PR description; attach screenshots or response logs for UI or transport changes.
- Confirm `npm run build` succeeds and mention any manual verification steps completed.
- Align with `CONTRIBUTING.md` and the Code of Conduct; request review when documentation and security notes are up to date.

## Security & Configuration Tips
- Manage secrets via environment variables expected by `src/config.ts` (e.g., `CLICKUP_API_KEY`, `CLICKUP_TEAM_ID`, `ENABLE_SSE`).
- Use `scripts/generate-ssl-cert.sh` if you need local HTTPS, and update `SECURITY.md` when adding new toggles or hardening steps.
- Never commit generated credentials, and document new configuration keys in `README.md` plus `docs/` where appropriate.

## CRITICAL: Use ripgrep, not grep

NEVER use grep for project-wide searches (slow, ignores .gitignore). ALWAYS use rg.

- `rg "pattern"` — search content
- `rg --files | rg "name"` — find files
- `rg -t python "def"` — language filters

## File finding

- Prefer `fd` (or `fdfind` on Debian/Ubuntu). Respects .gitignore.

## JSON

- Use `jq` for parsing and transformations.

## Install Guidance

- macOS: `brew install ripgrep fd jq`
- Debian/Ubuntu: `sudo apt update && sudo apt install -y ripgrep fd-find jq` (alias `fd=fdfind`)

## Agent Instructions

- Replace commands: grep→rg, find→rg --files/fd, ls -R→rg --files, cat|grep→rg pattern file
- Cap reads at 250 lines; prefer `rg -n -A 3 -B 3` for context
- Use `jq` for JSON instead of regex
